# AGENTS.md

## What this is

WhateverPad PS5 is a fork of AnyPad PS5 by elmonomalva0, under GPL-3.0-or-later,
and anything you change here gets its verdict from the owner's real PS5, not from
a test run on the PC. It ships as one payload ELF for a jailbroken PlayStation 5
and connects third-party Bluetooth gamepads, both Bluetooth Classic and Bluetooth
LE with HID over GATT, to the console's own Bluetooth chip, shares that chip with
the system driver, and presents each pad as a virtual DualSense of the main user.
The DualSense is meant to keep working beside it; rule 8 covers the one case that
still breaks.

Version comes from `src/version.h` only (currently `0.9.5-beta`). Upstream was
tested on firmware 10.01. Behaviour on firmware 13.60 is unproven until the
owner's own console runs say otherwise.

## Layout

```
src/
  ps5_main.c   the payload loop: start order, stop flag, rest-mode shutdown
  host.c, le.c Classic and LE: discovery, pairing, L2CAP, SDP, HID over GATT
  profiles.c   one profile per controller family: ids, reports, rumble, lights
  generic.c    any other HID pad, read from its own descriptor
  hci_usb.c, usb_desc.c, evstream.c   the chip over USB, endpoints, events
  ps5_vpad.c   the virtual DualSense each pad drives
  web.c        the page's HTTP server and its API
  launcher.c, ps5_ui.c, ps5_apps.c   the media-row tile
  config.c, hotkey.h, netinfo.c, lock.c   settings, held-button detection,
                                          local address, one instance only
  log.c        the log file, its size rotation, and the ring behind /api/live
  web_page.c, icon_data.c   generated by make (web/index.html, assets/icon0.png)
tests/         eight plain-C unit test binaries run by make test; one real
               descriptor dump in fixtures/, a stand-in sys/sysctl.h in host/
tools/         build-elf-docker.sh (payload in a container), live.sh (the API)
web/           index.html, embedded into the payload at build time
maps/          optional per-pad mapping files
```

Never edit `src/web_page.c`, `src/icon_data.c`, `dist/` or `build/` by hand.

## Commands

Run from the repository root.

```sh
make test                    # the eight host unit tests, about 3 s, exit 0
make fuzz                    # the same parsers under ASan/UBSan, 200000 inputs, about 3 s
make ps5 PS5_PAYLOAD_SDK=/path/to/ps5-payload-sdk   # the ELF lands in dist/
make send PS5_HOST=<console ip> PS5_PAYLOAD_SDK=/path/to/ps5-payload-sdk
tools/build-elf-docker.sh /path/to/ps5-payload-sdk [image]
```

`tools/build-elf-docker.sh` needs an unpacked SDK release and an image with
clang-18 and lld-18. It prints the SHA-256 and leaves
`dist/WhateverPad-PS5-<version>.elf` and its `.sha256`, built from a
`build/build_id.h` that carries the commit.

`make send` and every `curl` against the console touch the real PS5: owner's go first.

## The page and the API

The page is served on port 8095 (`src/web.h`) and can be opened from the media
row on the console, or from a phone on the same network at the console's IP.
`tools/live.sh` wraps it: `WHATEVERPAD_IP=<console ip> tools/live.sh
watch|state|settings|set|hci|pair|stop`.

- `GET /api/tune` reads the runtime settings; `POST /api/tune?name=value` changes
  one. `trace` is one of them: `POST /api/tune?trace=1` turns the HCI event trace
  on.
- `POST /api/stop` stops the payload cleanly; the page's Stop button sends it. A
  `stop` flag file under `/data/whateverpad/` does the same.
- Only POST changes anything, and every POST needs the header `X-WhateverPad: 1`.
  Without it the server answers 403.
- `POST /api/pscombo?slot=N&combo=...` sets the buttons that stand in for PS on
  that pad: one to three names separated by commas (`l1,l2,options`), `none` to
  remove it, `capture` to record a new one on the pad for 60 s.
- The other routes and methods are in `handle()` in `src/web.c`: `live`, `state`,
  `log`, `pair`, `forget`, `ps`, `retry`, `hci`. `0x0C03` (Reset) is refused.

## The log and the state folder

WhateverPad writes `/data/whateverpad/whateverpad.log`, one line per event,
flushed after each line. The file rotates at 1 MiB: the old content becomes
`whateverpad.log.1` and the previous `.1` is dropped. The same lines also live in
a 600 line ring in memory, which is what `/api/live` serves.

Under `/data/whateverpad/`: `config.ini` (settings), `pads.db` (pairings),
`ps_combos.txt` (the PS combination, per pad model), the presence flags `stop`,
`pair` and `no_icon`, and `bind_user`. `bind_user` is not a flag: it holds a
value, `other` or a hexadecimal user id, that overrides which signed-in user gets
the virtual pads (see `vpad_choose_user` in `src/ps5_vpad.c`).

## Working rules

### 1. Only the owner's console accepts a change

Bluetooth and controller behaviour counts as working only after the owner runs
the exact ELF on his real PS5 and answers a yes/no question. A log line is
evidence for the next hypothesis, never a yes on its own. No simulator, fixture
radio, host stand-in, probe kit or generated page counts as proof of behaviour.

### 2. Fresh work, and only the two fixes

Every fix is written fresh on the reset `main`. Never port code, tests or designs
from the discarded branches or worktrees (ownership ledger, session lifecycle,
attrib, probes, RSSI inquiry build, traffic tolerance, bond-store rewrite, S3
kit, old foundation plan); research may inform a new design, but the code is
written here. The current plan allows exactly two fixes: third-party pad pairing
on firmware 13.60, and the native DualSense reconnect. Anything else needs the
owner's decision.

### 3. The fix loop, in this order

1. Read the console log from the failing run.
2. Write a unit test from the values in that log, or from the real event bytes,
   and watch it fail. RED means an assertion failure. A compile error is not RED.
3. Change the smallest amount of code, in a pure decision function that takes
   the values and times as arguments and that production actually calls.
4. The owner checks that ELF on the console and answers yes or no.
5. Bump the patch in `src/version.h` (`0.9.5-beta` is the baseline; a fix makes
   `0.9.6-beta`) and add the change to `CHANGELOG.md` in English and Spanish.
6. Open a pull request for that one fix and merge it with a regular merge commit.

If the answer is no, take the next hypothesis from the new log. After three
failed hypotheses, stop and report instead of guessing again.

### 4. Tests test real code

`make test` must stay fast, and every test feeds real code: parsers, mappings,
encoders, decision functions, given bytes or a configuration file, with the
result checked. No sentence or prose matching tests. `make test` must pass
before a pull request and on the CI run. Use the targets that exist; do not add a
framework, and do not add a dependency for a few lines.

### 5. Console work

One step at a time, each with the owner's go for that step. Before any load that
can search for pads, the owner answers these, and the answers are recorded:

- "DualSense is off and not pairing", in those exact words.
- The third-party pad is off.
- For a baseline run, the PS5 was fully restarted (not Rest Mode) and the
  jailbreak was run again.

A vague "done" or "ok" is not enough; ask again.

Every console step has a run sheet in `.omo/evidence/whateverpad-baseline-reset/`
(`task-<N>-<name>.md`) holding: the ELF identity (commit, tree, size in bytes,
SHA-256, the banner line the build prints at startup); the rollback copy path;
the SHA-256 read back from the console; each owner answer copied verbatim with
its UTC time; and the log interval from `/data/whateverpad/whateverpad.log`.

To install: copy the installed ELF and its `meta.json` into a new
`~/ps5/backup/whateverpad-before-<sha12>/`, delete then write the new ELF under
the same filename, read it back and compare SHA-256. One `/loadpayload` per test;
the rollback is loading the saved ELF back. Never change the autoload list, never
edit the system's Bluetooth bonds, never ask for a hypervisor, and never write
the console's IP address into the repository.

Build every console ELF with `tools/build-elf-docker.sh` from a clean worktree. An
ELF the owner accepted from a pull request head stays the released ELF after the
regular merge only when `git diff --quiet <PR head> <merge commit>` holds;
otherwise rebuild from `main` and ask that todo's questions again.

### 6. Git, branches and what is never deleted

- Every branch is named after what it implements, and every merge is a regular
  merge commit. No squash, no rebase merge.
- Plain messages: no `Co-authored-by`, no AI attribution in commits, pull
  requests or reviews.
- CI runs on push to `main` and on `pull_request`, never twice for one change.
- Keep the GPL-3.0-or-later notices, the credit to AnyPad PS5 by elmonomalva0,
  and the owner's WhateverPad name and icon.
- Never alter or delete existing files under `~/ps5/updates/bisect/`,
  `~/ps5/backup/` or `.omo/evidence/`. New evidence goes to
  `.omo/evidence/whateverpad-baseline-reset/`, new backups to new
  `~/ps5/backup/whateverpad-before-<sha12>/` folders.
- Never run `git clean -x` or `git clean -X`, and never delete
  `/home/andres/ps5/build/whateverpad-wt/` as a whole.
- Do not delete a worktree or a local branch you did not create without the
  owner's decision. After a merge, remove only that pull request's own worktree
  and its branches.

### 7. Talking to the owner

Plain words, no jargon, and never make him feel stupid. He tests standing about
30 m from the PC, so every check is a simple yes/no he can answer from where he
stands: press this, tell me what you see. No camera, no screen capture, no
calibration step.

### 8. Known issue and firmware

An inherited upstream issue is still open: if the DualSense is switched off while
WhateverPad is running, it can blink blue and stop responding until the console
restarts. The README says so in both languages and keeps saying so until the
owner confirms a fix on his console. Firmware 13.60 support is likewise unproven
until then.
